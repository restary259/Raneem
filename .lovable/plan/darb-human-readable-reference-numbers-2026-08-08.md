# Darb — Human-readable reference numbers

## Findings (scanned before proposing)

### What already exists
- **Cases already have a reference.** `cases.case_reference` is generated by the `assign_case_reference()` trigger on insert:
  `DRB-<YYYY>-<6-digit sequence>` (e.g. `DRB-2026-000042`), year from Asia/Jerusalem, counter from `case_reference_seq`, unique index `idx_cases_case_reference`. Existing rows were backfilled in creation order.
- It is displayed in: case detail header (falls back to `#<uuid first 8>`), team work page, admin command center, payout dialog and payout chat card (per linked case), partner profile panel, and `search_cases_for_mention` (the `#` chat mention already matches on reference or the first 8 chars of the UUID).

### What is missing
- **`payout_requests` has no reference column.** Confirmed by querying `information_schema`: the only ref-ish column is `transaction_ref`, which is the *bank* reference an admin types in after paying — not an ID for the request itself. Requests are identified by raw UUID everywhere (chat card, admin list, spreadsheet `payouts` sheet exports `id` = UUID).
- **`rewards` has no reference** either (only `referral_id`). Rewards are internal rows tied to a case, so they do not need their own public number — the case reference plus the payout reference covers them.
- **Search does not cover references.** `AdminPipelinePage` filters on `full_name` and `phone_number` only — typing `DRB-2026-000042` finds nothing. The payouts list and the spreadsheet hub filter on the columns they render, and neither renders a reference.
- **Spreadsheet/export**: `fetchPayoutsSheet` returns `id` (UUID) and never surfaces the case reference; `fetchCommissionsSheet` derives its "source" text from `rewards.admin_notes` free text. So an exported Excel row cannot be tied back to a case by reference.
- **Chat payout card** shows amount, case count and per-case case references, but no reference for the payout request itself — which is exactly the number needed when sending the transfer.

## Proposed format

Keep the existing `DRB-YYYY-NNNNNN` shape and add a sibling for payouts, so both read the same way:

```text
Case    DRB-2026-000042      (already live, unchanged)
Payout  PAY-2026-000017      (new)
```

- Same construction: prefix + Jerusalem year + zero-padded sequence from a dedicated Postgres sequence, assigned by a BEFORE INSERT trigger, unique index.
- 6 digits, no ambiguous characters, no randomness — sequential, sortable, short enough to say out loud ("pay two-six, seventeen").
- Search is case-insensitive and tolerant: typing `17`, `000017`, `PAY-2026-000017` or `pay 2026 000017` all match.

## Implementation plan

### 1. Database (one migration)
- `CREATE SEQUENCE public.payout_reference_seq;`
- `ALTER TABLE public.payout_requests ADD COLUMN payout_reference text;`
- `assign_payout_reference()` trigger (BEFORE INSERT, `SET search_path = public`) mirroring `assign_case_reference()`, using `requested_at`/`now()` for the year.
- Backfill existing rows in `requested_at` order, `setval` past the backfill, then `CREATE UNIQUE INDEX idx_payout_requests_reference`.
- Add a `text_pattern_ops`/lower index on `cases.case_reference` and `payout_requests.payout_reference` so `ILIKE '%…%'` search stays fast.
- Update `list_payout_requests()`, `get_payout_request_detail()`, `get_my_payout_preview()` and `list_partner_directory()` to return `payout_reference`.
- `request_payout_via_chat()` writes the reference into the payload of the chat message it posts, so the card can show it without a second read.

### 2. Search
- Shared helper `src/lib/reference.ts`: `normalizeRef(input)` (upper-case, strip spaces/dashes) and `matchesRef(ref, query)` so every list uses one rule.
- `AdminPipelinePage`: extend the filter to `case_reference` and update the placeholder to "name, phone or reference".
- Admin payouts (`PartnersDirectory` + the requests lists) and `PartnerProfilePanel`: search box matches partner name, email and `payout_reference`.
- Spreadsheet hub: reference becomes a normal searchable column, so the existing filter covers it.
- `search_cases_for_mention` already matches the case reference — no change.

### 3. Display
- **Payout chat card** (`PayoutRequestCard`): reference shown as a mono badge at the top next to the status, with a copy-to-clipboard button; also in the dialog header. This is the "glance before sending the transfer" surface.
- **Partner earnings page**: each request row shows its reference so the partner can quote it back.
- **Partner profile panel / payout history**: reference column, first in the row.
- **Case detail header**: unchanged (already shows the case reference); drop the `#<uuid>` fallback since every case now has a reference.
- **Finance dashboard**: payment/payout rows show the case reference and, where applicable, the payout reference.

### 4. Exports
- `fetchPayoutsSheet`: replace the UUID `id` with `payout_reference`, add a `case_references` column (joined from the linked rewards) and keep `transaction_ref` as the separate bank field.
- `fetchCommissionsSheet` and the payments sheet: add a `case_reference` column sourced from the case row instead of parsing `admin_notes`.
- Column labels added to `sheets.col.*` in both `ar` and `en`; references render as ASCII/LTR mono even in the RTL sheet.

### 5. Tests
- Unit test for `normalizeRef`/`matchesRef` (spaces, dashes, lower case, bare digits).
- i18n key coverage test picks up the new labels automatically.

## Technical notes
- One migration; no change to money logic, `record_case_commission`, reward amounts or referral attribution — `COMMISSION_RULES.md` is untouched.
- `transaction_ref` keeps its current meaning (the bank's own reference) and is never conflated with `payout_reference`.
- Numbers/dates stay `en-US` ASCII per project convention; the reference is always rendered LTR.
